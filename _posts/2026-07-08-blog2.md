### Going Beyond the Schema: Fixing an Upstream Kernel Bug

One of the most exciting developments during this phase was realizing that schema work often leads you directly into the actual driver code. While working on the crossbar bindings, I  fixed a critical bug in the irq-crossbar driver.

* **[PATCH v2 1/2] irqchip/crossbar: Use correct index in crossbar_domain_free()**

* **[PATCH v2 2/2] irqchip/crossbar: Fix parent domain resource leak**


#### The Problem
In the crossbar driver, `crossbar_domain_free()` resets the domain data and then uses the nulled-out `irq_data->hwirq` member as an index to reset the `irq_map[]` entry and write the relevant crossbar register with a safe entry. That meant it **never freed the correct index** and kept the crossbar register connection to the source interrupt active.

If it hadn't reset the domain data, the situation would have been even worse: `irq_data->hwirq` holds the source interrupt number, but both the map and register index need the corresponding GIC SPI (General Interrupt Controller Shared Peripheral Interrupt) number, not the source interrupt number. This could even result in an out-of-bounds access since the source interrupt number can be higher than the maximal index space.

Also irq_domain_alloc_irqs_parent() is called in allocate_gic_irq() but
irq_domain_free_irqs_parent() is never called which causes resource
leak.

#### The Fix
I fixed this issue by modifying the driver to explicitly use the GIC SPI index from the parent domain's `irq_data`. and Fixed the resource leak by calling irq_domain_free_irqs_parent() in
crossbar_domain_free().
